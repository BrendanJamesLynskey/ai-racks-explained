<Layer kind="concept">

Serving a large model has two phases with opposite needs. **Prefill** reads the whole prompt in one pass: thousands of tokens share each weight read, so it is limited by compute. **Decode** produces one token per request per step, re-reading the weights and the request's KV cache each time, so it is limited by memory bandwidth. Run both on the same GPUs and each gets in the other's way: a long prefill stalls every decode stream batched with it. **Disaggregated serving** gives each phase its own pool of GPUs and moves each request's KV cache from the prefill pool to the decode pool after its first token (DistServe and Splitwise, both 2023-24 papers; [Serving, chapter 11](https://llm-inference-explained.vercel.app/learn/11-why-disaggregate) explains why).

A rack is a natural unit for it. Inside one NVL72-class rack every GPU is one NVLink switch hop from every other, so the KV hand-off never touches the network.

**The simulated rack.** The animation runs [Disaggregated_Inference_Sim](https://github.com/BrendanJamesLynskey/Disaggregated_Inference_Sim), a discrete-event simulator with a published validation section, in your browser: its own JavaScript engine, vendored byte for byte at commit <V of="dis.meta.commit" fmt="raw" /> and checked here to reproduce its Python package bit for bit. The rack is <V of="dis.meta.gpus" fmt="int" /> GPUs of the simulator's GB200 preset, one Blackwell GPU of a GB200 superchip (<V of="dis.meta.gb200_mem" fmt="bytes" /> and <V of="dis.meta.gb200_bw" fmt="rate" /> each, NVIDIA's per-GPU figures) as <V of="dis.meta.instances" fmt="int" /> instances of <V of="dis.meta.tp" fmt="int" />, tensor-parallel over NVLink, serving Llama 3 70B. <V of="dis.meta.n" fmt="int" /> requests arrive at <V of="dis.meta.rate" fmt="int" /> a second, with prompts of <V of="dis.meta.prompt_mean" fmt="int" /> tokens and outputs of <V of="dis.meta.output_mean" fmt="int" /> on average. The SLOs: first token within <V of="dis.meta.ttft_slo" fmt="time" />, then <V of="dis.meta.tpot_slo" fmt="time" /> a token at most.

**Sizing the pools.** That load asks for <V of="dis.meta.prompt_tok_s" fmt="int" /> prompt tokens a second of prefill and <V of="dis.meta.offered_tok_s" fmt="int" /> output tokens a second of decode. With 6 prefill and 12 decode instances, prefill cannot keep up: requests queue, TTFT reaches <V of="dis.6-12.nvlink.gb200.ttft_p99" fmt="time" /> at the 99th percentile and only <V of="dis.6-12.nvlink.gb200.slo" fmt="pct" /> of requests meet both SLOs, while the decode pool idles at <V of="dis.6-12.nvlink.gb200.tpot_p50" fmt="time" /> a token. Moving instances to prefill brings TTFT down to <V of="dis.12-6.nvlink.gb200.ttft_p99" fmt="time" /> at 12:6. Every instance taken from decode makes each decode instance batch more streams, so time per token rises: <V of="dis.12-6.nvlink.gb200.tpot_p99" fmt="time" /> at 12:6, <V of="dis.14-4.nvlink.gb200.tpot_p99" fmt="time" /> at 14:4. The right split follows the workload's prompt-to-output ratio, which is why disaggregated serving systems resize their pools as traffic changes.

**The KV hand-off.** Llama 3 70B's cache is <V of="dis.meta.kv_per_token" fmt="bytes" /> a token, so an average prompt hands over <V of="dis.meta.kv_mean" fmt="bytes" />. From a prefill instance's four GPUs that takes <V of="dis.link.nvlink.kv_time" fmt="time" /> over their NVLinks, <V of="dis.link.ib.kv_time" fmt="time" /> over their four 400 Gb/s network ports (the path between racks), and <V of="dis.link.eth100.kv_time" fmt="time" /> over a single 100 GbE port. The simulator measures the same means, queueing included: <V of="dis.12-6.nvlink.gb200.handoff_mean" fmt="time" />, <V of="dis.12-6.ib.gb200.handoff_mean" fmt="time" /> and <V of="dis.12-6.eth100.gb200.handoff_mean" fmt="time" />. The hand-off delays each request's second token, so it counts in time per output token (the simulator follows DistServe's definition); spread over <V of="dis.meta.output_mean" fmt="int" /> output tokens it costs little here: <V of="dis.12-6.eth100.gb200.tpot_p99" fmt="time" /> against <V of="dis.12-6.nvlink.gb200.tpot_p99" fmt="time" /> at the 99th percentile. It matters more for long prompts with short answers, and when a pool's port is shared. [Serving, chapter 12](https://llm-inference-explained.vercel.app/learn/12-moving-the-kv-cache) and [Inference Trade-offs, chapter 6](https://inference-tradeoffs-explained.vercel.app/learn/06-kv-handoff-and-compression) go further.

**Context-optimised parts.** If prefill is compute-bound, it does not need HBM. NVIDIA has announced Rubin CPX, a GPU with <V of="dis.meta.ctx_mem" fmt="bytes" /> of GDDR7 instead of HBM for "massive-context" prefill, expected at the end of 2026 (planned, not shipping). The simulation's context-optimised part is illustrative, not CPX: the rack GPU's own compute (the GB200 preset's), so that it differs from the rack's GPUs in memory only, with <V of="dis.meta.ctx_mem" fmt="bytes" /> of memory at <V of="dis.meta.ctx_bw" fmt="rate" />, a GDDR7-class bandwidth chosen by us, since NVIDIA states none. Put it in the prefill pool and TTFT barely moves (<V of="dis.12-6.nvlink.ctx-prefill.ttft_p99" fmt="time" /> against <V of="dis.12-6.nvlink.gb200.ttft_p99" fmt="time" />). Put it in the decode pool and time per token rises to <V of="dis.12-6.nvlink.ctx-decode.tpot_p99" fmt="time" />: only <V of="dis.12-6.nvlink.ctx-decode.slo" fmt="pct" /> of requests meet the SLOs. That asymmetry is the case for building different hardware for each pool ([Inference Trade-offs, chapter 5](https://inference-tradeoffs-explained.vercel.app/learn/05-heterogeneous-and-optical-pools)).

**The software that schedules it.** Production systems route each request to a prefill worker, move its cache, and hand it to a decode worker, while watching both pools' queues. NVIDIA's open-source Dynamo describes itself as "the orchestration layer above inference engines" (vLLM, SGLang, TensorRT-LLM), with disaggregated serving and KV-aware routing among its features. The simulator's scheduler is far simpler: first come, first served in each pool, no routing by cache contents.

**Energy.** With the simulator's illustrative power coefficients, the rack spends <V of="dis.12-6.nvlink.gb200.j_per_tok" fmt="num" /> J per output token at 12:6, against <V of="dis.6-12.nvlink.gb200.j_per_tok" fmt="num" /> J at 6:12, where a backlog stretches the run out and idle power adds up ([chapter 6](/learn/06-power) on power, [chapter 11](/learn/11-cost) on cost).

<Layer kind="maths">

For a request with $L$ prompt tokens and a KV cache of $s_{\text{KV}}$ bytes a token, the hand-off over a link of bandwidth $B$ and latency $\ell$ takes

$$
t_{\text{hand-off}} = \ell + \frac{L\, s_{\text{KV}}}{B}, \qquad s_{\text{KV}} = 2\, n_{\text{layers}}\, n_{\text{kv heads}}\, d_{\text{head}}\, b,
$$

where $b$ is bytes per value (2 for BF16). For Llama 3 70B, $2 \times 80 \times 8 \times 128 \times 2 =$ <V of="dis.meta.kv_per_token" fmt="int" /> bytes. A decode step reads every weight and every running request's cache once, so with batch $n$ and context lengths $c_i$

$$
T_{\text{step}} \approx \frac{W + s_{\text{KV}} \sum_{i=1}^{n} c_i}{B_{\text{HBM}}},
$$

which is why decode wants HBM and prefill, $\approx 2 \times \text{parameters} \times L$ FLOPs per request, wants compute.

</Layer>
